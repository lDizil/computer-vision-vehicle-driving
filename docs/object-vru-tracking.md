# Объектный трек пешехода или велосипедиста

После эксперимента с двумя общими картами (#50) проверяем раздельное обнаружение и перенос **конкретных объектов**. Этот пилот работает офлайн; не меняет автомобильную голову Fast, токены штатного моста, Slow или `Safety Veto`.

## Наблюдения и треки

1. Закреплённый [TorchVision SSDLite / MobileNetV3](https://docs.pytorch.org/vision/0.15/models/generated/torchvision.models.detection.ssdlite320_mobilenet_v3_large.html) видит шесть исходных ракурсов в каждом из двух наблюдений и дополнительные перекрывающиеся кропы передних камер. Берём `person` и `bicycle`. Держим точный CPU-чекпоинт COCO локально, сверяем SHA перед открытием. Не переобучаем детектор и не переносим веса в репозиторий.
2. Переносим нижнюю середину восстановленной 2D-рамки на условную плоскость `z=0`. Обрезанные, крошечные и плохо обусловленные рамки не проецируем. Объединяем близкие попадания одной категории только из разных камер; сохраняем отдельные наблюдения для оценки движения. Наклон дороги, окклюзия ног и дрожание рамок дают метрическую ошибку; это не глубина от LiDAR.
3. Приводим прошлые наблюдения к **текущей** системе машины по ego-позам. Связываем только взаимно однозначные, близкие по координатам наблюдения одной категории с хотя бы одной общей камерой. Сравниваем режим геометрии и режим с дополнительным простым цветовым описателем из внутренней части рамки той же камеры. При неоднозначности, отсутствии общей камеры или расхождении скоростей не придумываем ID/скорость. Абстенция использует нулевое смещение в сравнении и отчитывается отдельно.

## Чему доверяем

Используем ровно development и heldout из #50: тот же набор осей, отсчёты +0,5/+1 с и физически раздельные записи. Сначала пишем сырые детекции, связи и скорости без меток. Только на development подбираем два коэффициента скорости вдоль луча/поперёк луча из фиксированной сетки `0, .25, .5, .75, 1`. Параметры замораживаем до прогноза heldout. Двойной слепой holdout фиксируем SHA до подключения целей.

Для оценки один раз сопоставляем текущие детекции с текущими аннотированными центрами; на **тех же** совпадениях сравниваем неподвижность, движения без калибровки и калиброванное движение. Не называем несопоставленную детекцию ложной: куратор разметки оставил только часть актуальных треков. Считаем ошибку смещения отдельно от ошибки будущего центра. Срез движения — истинное смещение ≥0,75 м, покоя — ≤0,25 м. Для сигнала нужны ≥20 однозначно связанных движущихся совпадений из ≥4 записей, выигрыш ≥0,10 м, ухудшение покоя не более 0,10 м и отсутствие роста средней ошибки положения. Это порог пилота, не критерий безопасности.

`python -m scripts.run_object_vru`: `capture` development → `calibrate` с SHA → `capture --gains` holdout дважды → сверяем файлы → `score` с SHA. Используем закреплённую CPU-среду; внутри контейнера сеть выключена, сырые JPEG и веса монтируются read-only, test labels нужны только оценщику.
