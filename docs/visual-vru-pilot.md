# Визуальная голова для пешеходов и велосипедистов

Обучаем небольшую визуальную голову для классов, которых нет в автомобильном детекторе Fast. Она оценивает, на каком участке перед машиной **сейчас** есть пешеход или велосипедист. DINOv2 заморожена: получаем шесть карт признаков и по калибровкам проецируем их на метрическую сетку 1 м. Свёрточная голова возвращает логит для каждой наблюдаемой ячейки. Это отдельный офлайн-пилот, а не замена штатных боксов, VLM или `Safety Veto`.

## Данные и проверка переноса

Фиксируем источники OpenScene Mini до оптимизации: четыре записи для fit, две отдельные записи для выбора эпохи и четыре другие записи для оценки. Источники закреплены по SHA, отбираем без вывода модели. Сохраняем настоящие текущие кадры, контрпримеры без объектов в коридоре и сцены с диагностическими парами. При отборе пар балансируем направления и предпочитаем окна, где совпадает метка фактического будущего, если есть опора. Это целевой набор, не случайная оценка частоты опасных событий. Координаты аннотированных центров, факт попадания во фрустум и метка нужного кандидата находятся отдельно от RGB. Фрустум не доказывает отсутствие окклюзии.

Фиксируем два зеркальных **пробных** пути из одной наблюдаемой продольной скорости. Пара попадает в эксперимент, когда по текущим аннотациям неподвижный бокс пешехода/велосипеда касается одного пути, но не другого, и нет смешения с контактом автомобиля. Это проверка геометрического различия при условии фиксированной текущей позы актёра. Дополнительно делаем отдельную сверку с будущими фактическими отсчётами 0,5–2,5 с, где можно проследить тех же актёров. Пути не рекомендуются для исполнения; допустимость полосы и реакцию других участников не оцениваем.

В `fit` используем баланс положительных/отрицательных ячеек и попарный loss при достаточной поддержке. Если наблюдаемой пары манёвров нет, берём пространственный запрос из фиксированных 5-метровых продольных полос: при одном занятом секторе ищем, слева он или справа. Проверяем такие запросы отдельно, максимум один на кадр. Эпоха выбирается по AP ячеек на development.

Держим два контроля: отдельную голову без карт камер (только позиция и геометрическая покрытость) и основную голову с картами другой записи. Ранжируем по максимуму логита на видимых ячейках, уникальных для пути или сектора. Общие ячейки не голосуют. Если у одного пути нет видимых эксклюзивных ячеек, оставляем результат неизвестным, не считаем его чистым.

Отдельно считаем AP по записям и точность выбора при равном весе левой и правой меток. Для подтверждения попарного визуального выигрыша нужны ≥10 пар в ≥3 записях, ≥3 пар с каждой стороной и преимущество не менее 10 п.п. над лучшим контролем. Гипотетический и фактический контакт учитываются раздельно.

## Запуск

`python -m scripts.run_visual_vru`: `prepare` → отдельные `capture` трёх разбиений → `fit` только с train/development → два `predict` с heldout без меток → фиксация SHA → `score`. Отбор читает закреплённые метаданные; снимки и метки размещает в разных каталогах. При захвате признаков метаданные и labels не монтируем. В предсказании участвуют только observation index, кэш признаков и замороженный fit. Результаты этого пилота не меняют решения агента.
