# VRU: фиксированный тест 80 из 120 клипов

Это проверка локализации и связи наблюдений дорожного объекта в ветке Fast Perception: пешехода или велосипеда. Она не измеряет корректность манёвров, работу Safety Veto или безопасность вождения.

## Что считается проходом

- Клип — три действительно полученных шестикамерных наблюдения около `t−1`, `t−0,5`, `t`. Опорное время OpenScene — время ассоциированного LiDAR-отсчёта, не измерение синхронности экспозиций камер. В модель не поступают LiDAR, будущие кадры и разметка.
- Метки задают одну основную цель до инференса. Остальные размеченные цели остаются кандидатами сопоставления: связь нельзя засчитать, подменив один объект другим. Все позиции сравниваем в текущих координатах машины.
- Зачёт: текущая детекция правильного класса однозначно сопоставлена основной цели в пределах 2 м (с тем же двусторонним зазором 0,25 м), и цепочка причинных связей содержит хотя бы одно прошлое совпадение с этой же размеченной целью. Если любой связанный прошлый центр однозначно относится к другой цели, клип не проходит. Неизвестный центр не считается подтверждением.
- Знаменатель — все 120 клипов, включая пропуски, дальние и плотные случаи. Порог — 80. Сопоставленную историю не считаем доказанным физическим ID или проверенной точностью скорости. Группируем ошибки по поездке и диапазону расстояния.

## Данные и граница разработки

Исходная выборка — [OpenScene v1.1 Mini](https://github.com/OpenDriveLab/OpenScene/blob/main/docs/getting_started.md), реальные камеры и 3D-метки nuPlan. План выбирается только по закреплённым метаданным, с разбиением «день + машина», без прогнозов. Он не пересекается по этой группе с 23 ранее закреплёнными источниками проекта. Есть 40 клипов с основным объектом в каждом диапазоне `[2,8)`, `[8,16)`, `[16,27)` м, шесть групп поездок и ≥3 с между опорными точками внутри группы. Среди целей — 73 движущихся, 37 стоящих, 10 промежуточных. Это выборка для диагностики, а не модель частот в реальном движении. Нахождение 3D-бокса во фрустуме не гарантирует видимость в RGB.

Для закреплённого плана `5d8f9954e5185ea59e612cb323b255bb2aa70a07f9077da9cd410360c10faacc` извлекли 2160 JPEG из четырёх архивов (11,09 ГБ загрузки). Инференс читает только `inputs/`, а метки отдельно прикреплены SHA-256 индекса. Веса и изображения не выкладываем в репозиторий.

Альтернативы:

- [nuScenes](https://openaccess.thecvf.com/content_CVPR_2020/html/Caesar_nuScenes_A_Multimodal_Dataset_for_Autonomous_Driving_CVPR_2020_paper.html) уже даёт шесть камер и 3D-треки. Но в имеющемся Mini при нашем ROI и интервале 3 с найдено максимум 28 подходящих клипов даже без проверки видимости; подходит для небольшого переноса, не для замены этого контроля.
- [Argoverse 2 Sensor](https://www.argoverse.org/av2.html#sensor-dataset) даёт независимые 3D-треки, другие города, другой риг и карты высоты грунта. Имеет смысл как отдельная внешняя валидация после адаптера и замера в нашей метрике; не смешиваем с результатом OpenScene.

## Решения, которые сравниваем

| Метод | Зачем и какое ограничение проверяем |
|---|---|
| SSDLite + Faster R-CNN, пересечение с плоскостью дороги | Исходный метод без поправок и без смены трекера. |
| [D-FINE-M](https://github.com/Peterande/D-FINE#model-zoo) с полной картинкой | Меняем поиск бокса, оставляем старую геометрию. Авторы меряют COCO, не наши клипы. Версию Objects365→COCO используем только в локальном исследовании; набор условий upstream не заменяем лицензией нашего кода. |
| [Depth Anything V2 Metric Outdoor Small](https://github.com/DepthAnything/Depth-Anything-V2/tree/main/metric_depth) | Те же 2D-боксы, оценка оптической глубины по каждому кадру. Метрический checkpoint обучался на Virtual KITTI 2; перенос абсолютного масштаба на наш риг проверяем, а не предполагаем. |
| [Apple Depth Pro 2-S Core ML](https://huggingface.co/apple/DepthPro2-coreml) | Известный `fx` каждой камеры и отдельное хронологическое состояние на камеру, сброс между клипами. Модель получает только настоящий и предыдущие кадры. Исследовательские веса по [лицензии Apple](https://github.com/apple-aiml-research/ml-depth-pro-2/blob/main/LICENSE_MODEL). |
| D-FINE-M с перекрывающимися кропами | Для мелких объектов сравниваем полные виды + фиксированные кропы фронтальных камер; возвращаем боксы в исходные координаты и удаляем видимые дубли. [SAHI](https://arxiv.org/abs/2202.06934) обосновывает проверку slicing; не переносим его численные результаты на наше видео. |
| [SAM 2.1 Tiny](https://huggingface.co/facebook/sam2.1-hiera-tiny) поверх боксов | С контрольным Depth Pro 2 сравниваем пиксели внутри сегментированной фигуры с прямоугольным семплом той же области. Маска — только покадровая, без меток и будущих изображений. Если маска не подтверждена, возвращаемся к исходному прямоугольному измерению. |
| [Metric3Dv2 ONNX](https://github.com/YvanYin/Metric3D#improved-onnx-checkpoints-available-now) | Резервный независимый калиброванный depth baseline. Выход в канонической системе, нужен пересчёт масштаба по `fx`; просто считать его метрами нельзя. |
| [BEVFormer](https://github.com/fundamentalvision/BEVFormer) / [Cube R-CNN](https://github.com/facebookresearch/omni3d#installation) | Прямой 3D-подход, не другая LLM. Публичные стеки CUDA-ориентированы; модель nuScenes не считаем готовой для OpenScene и Mac без отдельной проверки адаптера. |

## Первое измерение на development

Из 51 прежнего окна 36 имеют пригодную основную цель такого же вида во всех трёх кадрах. Это набор разработки, **не** контрольная 120-ка, распределение 6/9/21 по дальности. Победитель не назначается по одной только 2D-точности.

| Вариант на одних наблюдениях | Текущий центр совпал | Клип прошёл |
|---|---:|---:|
| Прежнее объединение SSDLite + Faster R-CNN | 8 | 1/36 |
| D-FINE-M и прежняя нулевая плоскость | 7 | 3/36 |
| D-FINE-M и поправка −0,190 м из прежних поездок | 12 | 6/36 |
| D-FINE-M + Depth Anything V2 Metric | 1 | 1/36 |
| D-FINE-M + Depth Pro 2-S | 12 | 4/36 |

Из 36 текущих основных целей у 22 есть бокс D-FINE того же класса с IoU ≥0,30 против проекции 3D-разметки (диагностический сигнал, не ручная 2D-разметка). Этого не хватает, чтобы решать задачу только сменой глубины. У сопоставленных фронтальных боксов Depth Anything типично завысил глубину (медиана отношения к разметке ~1,30, 17 случаев с доступным сэмплом), поэтому готовый checkpoint нельзя считать откалиброванным на наших кадрах.

Перекрывающиеся кропы улучшили нулевую геометрию D-FINE с 3 до 5 проходов, но не лучший вариант: с поправкой высоты 5 вместо 6, с Depth Pro 2 — те же 4. Масштаб, оценённый только по другим поездкам development, поднял Depth Anything с 1 до 5. Два луча через верх/низ бокса и типичная высота класса, оценённая по #54, дали 7/36 на полных видах и 6/36 с кропами. Ни один из этих вариантов не прошёл порог для заморозки на контроле.

Маска SAM 2 изменила проецированные результаты в 75 из 152 наблюдений (при неизменных боксах и Depth Pro 2), но не добавила ни одного пройденного development-клипа: 4/36 до и после. Даже если задним числом выбирать удачный вариант отдельно для каждого development-клипа, объединение всех испытанных вариантов даёт совпавший текущий центр у 26/36, а проход — лишь у 13/36. Это диагностический максимум только для проверенных подходов, не результат рабочей системы. Продолжать подбирать один порог расстояния на этих данных бессмысленно.

Для следующего цикла `plan-development` выбрал 60 клипов из шести старых групп по двум закреплённым манифестам: 20/20/20 по дальности, 40 движущихся, 16 стоящих и 4 промежуточных. Нужны только уже локальные архивы 3, 5, 22. Это данные разработки: часть этих поездок ранее участвовала в оценке геометрии. Для них есть отдельные `prepare-development` и `score-balanced-development`; контроль не меняем.

Исходное объединение уже выполнило инференс на всех 120 клипах без меток; SHA прогноза `1018a17ad70ddba8a27b3eef3503d5be76bea406f618fce4d6242cc938d7fe`. Повтор выбора совпал с исходным планом байт-в-байт. Число пройденных контрольных клипов пока не вычисляли.

## Диагностика дальности на development‑60

Те же 60 клипов, все основные цели — пешеходы. Для первых четырёх строк сохраняем исходные пиксели и входы: D-FINE 640×640, Depth Pro 2 Core ML 640×360, W4, отдельное состояние камеры. [D-FINE-X](https://huggingface.co/ustc-community/dfine-xlarge-obj2coco) и [Depth Pro 2-B](https://huggingface.co/apple/DepthPro2-coreml) — закреплённые исследовательские чекпойнты; опубликованные COCO AP и метрики глубины не являются зачётом этого теста.

| Вариант | Прошло из 60 | Дальние, из 20 |
|---|---:|---:|
| D-FINE-M + S | 22 | 1 |
| D-FINE-M + B | 17 | 1 |
| D-FINE-X + S | 20 | 0 |
| D-FINE-X + B | 17 | 1 |
| D-FINE-X, крупнее ректификация и вход 960×960 + S (прототип) | 22 | 1 |
| M + S с обученной поправкой оптической глубины (прототип) | **25** | **2** |

Из 16 дальних пропусков текущего центра у M+S в 9 нет бокса того же класса с IoU ≥ 0,30 к проекции кубоида, в 4 такое сопоставление неоднозначно. У остальных трёх есть однозначная 2D-пара: одна не дала принятую точку глубины, ещё две ошибки превышают 2 м. Это диагностика по проекциям, не разметка видимости. Даже выбор исторических связей по ответу при неизменных 3D-точках ограничен 26/60.

Поправка `z' = 0,870159·z + 1,054204 м` получена по 53 однозначным 2D-парам из четырёх других старых групп и применена без обучения на этих 60. Она вернула четыре клипа и потеряла один по сравнению с M+S. Только одна обучающая пара относилась к велосипеду, поэтому переносимость на него не подтверждена. Отдельно подготовлены 48 клипов из этих четырёх групп для обучения: 16 в каждом диапазоне, 864 JPEG и локальные проекции 3D-кубоидов. Проекции не считаем размеченными видимыми 2D-боксами.

Прототипы не включены в допущенные варианты контрольного прогона. Порог разработки 40/60 не пройден. Для заморозки любой DP2-связки проверяем ревизии detector/depth capture и хеши манифеста, реально скомпилированного бандла и воркера; другой вариант отвергается до чтения контрольных меток. Ранее измеренные артефакты остаются доступны для development-пересчёта.

## Как воспроизводим

1. В проверенном Linux-образе `scripts.run_vru_120 plan` затем `prepare`. Привязка к manifest, целым архивам, выбранным членам и каждому JPEG.
2. Нативно в выделенном окружении `requirements/vru-120-mac.txt`: `capture-candidate` (`--split development` или `control`); опционально `capture-depthpro` с собранным Swift-воркером и закреплённым Core ML-пакетом. Входы должны иметь одинаковый SHA снимков.
3. `score-development` использует только прошлые наборы. Перед открытием контрольных ответов замораживаем выбранную сборку, параметры и SHA через `freeze-release`; минимальный порог разработки — ⅔ на достаточном наборе.
4. `capture-baseline` на тех же 120 clip inputs, без меток. `score-control` допускает только зафиксированный план и выбранный на development вариант. Проверка SHA и поз обеих систем предшествует открытию меток. Лишь этот этап может подтвердить 80/120.
